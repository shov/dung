# Dung — ⚠️ SPIKE / THROWAWAY ⚠️

Одноразовый прототип. Отвечает на один вопрос: **успевает ли Claude генерировать связный и играбельный
top-down мир на лету?** Код не для продакшена; в `main` попадут только выводы (спека, ADR).

## Запуск

```bash
npm install
npm start              # сервер ws://localhost:8787 + клиент, сам открывает браузер
npm run dev            # то же с перезапуском при правках кода, без открытия браузера
npm test               # движок правил и починка проходимости
```

Нужен залогиненный Claude Code CLI: генерация идёт через `claude -p` по подписке, API-ключ не нужен.
Если команда называется иначе (алиас, другой `CLAUDE_CONFIG_DIR`), задай `CLAUDE_CMD` в `.env`
(шаблон — `.env.example`).

## Управление

WASD/стрелки — шаг, Space — взаимодействие (с выбранным предметом — применить его), Tab — сменить предмет,
E/Q/F/R/1-4 — ситуативные действия мира (подсказки внизу), F3 — отладка (очередь чанков, время вызовов).

## Свойства вместо подсказок

У каждого тайла и объекта есть набор скрытых свойств из закрытого словаря (`shared/src/schemas.ts`, `PROPERTIES`):
материал, физика, химия, магия. Правила матчатся по свойствам: «любое `sharp` на `plant+flexible` → убрать»,
поэтому любой острый предмет режет любой куст. Точные id — только для уникальных пар (ключ и его дверь).
Игрок свойств не видит: только сенсорное описание (вид, запах, на ощупь, температура) при осмотре, подборе и Tab.
Подсказки не раскрывают решений: легенда глаголов мира и нейтральное «Space: применить/осмотреть».
Если правила нет, Claude решает по свойствам и возвращает обобщённое правило; «ничего не происходит» тоже
запоминается, так что одна и та же ситуация никогда не спрашивает Claude дважды.

## Как устроено

- `shared/` — zod-схемы ответов Claude, типы мира, протокол WebSocket.
- `server/` — Node: игровая сессия, очередь генерации чанков (кольцо r=1, ≤3 параллельно, приоритет по направлению),
  детерминированный движок правил, починка проходимости flood-fill, вызовы `claude -p --json-schema`,
  сохранения в `saves-PROTOTYPE-wipe-me/<id>/` (`bible.json`, `chunks/`, `player.json`, `journal.jsonl`, `metrics.jsonl`).
- `client/` — Vite + PixiJS: рендер спрайтов из палитры, предсказание шага, HUD, блокирующий экран при лимите.

Метрики каждого вызова пишутся в консоль сервера (`[metric] …`) и в `metrics.jsonl` сохранения.

## Замеры спайка (2026-10-11, `claude -p` по подписке)

| Вызов | Модель / effort | Время | Заметки |
|---|---|---|---|
| Библия (со спрайтами в одном ответе) | Sonnet / default | 103 с | 14k output, **0 правил** — модель «выдохлась» на спрайтах |
| Библия (без спрайтов) | Sonnet / medium | 22–30 с | 8–10 правил |
| Чанк | Haiku / low | 15–16 с | ~2.5k **thinking**-токенов, CLI не даёт их выключить |
| Чанк | Sonnet / low | 5–13 с | 0 thinking, ~550–1650 output |
| 6 спрайтов | Haiku / low | 53–74 с | 10–15k thinking |
| 6 спрайтов | Sonnet / low | 9–20 с | |
| Импровизация | Sonnet / low | ~4 с | осмысленное правило с подсказкой решения |

Сквозной прогон ботом: до первого хода ~36 с (библия + стартовый чанк), 15 чанков подряд без заглушек,
бот ни разу не упёрся в недогенерированный край, починка проходимости нужна в ~1/4 чанков (1–3 клетки).

Выводы для следующего шага:
- Через CLI Sonnet на low быстрее Haiku 5.5 (тот всегда думает) — дефолт везде Sonnet.
- Спрайты отдельно и асинхронно, с плейсхолдерами: иначе библия медленная и теряет правила.
- Накладные расходы на запуск `claude -p` ~1–2 с на вызов; с API-ключом и SDK их не будет.
- Строгий enum в JSON-схеме заставлял CLI молча переспрашивать модель (num_turns 4, 54–67 с на библию);
  со свойствами-строками и фильтрацией на сервере — снова ~25 с.
- Предметы повторяются из чанка в чанк (лом/монета везде) — добавлена подсказка о частых типах, нужна проверка.
